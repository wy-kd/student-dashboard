# V2.2.1 — Tasks Workspace & Assignment Dialog Polish

No database migration, backend mutation/API, production dependency or existing-record rewrite is added. Existing Task/TodoItem models, assignment breakdown saving, progress/workload/StudySession accounting, authentication, reminders, Web Push, recurring scheduling, backup format, Windows launcher, Task Scheduler and Tailscale configuration are unchanged. No Spotify or unrelated features are included.

`jsdom` 26.1.0 is a pinned **development-only** dependency for React interaction tests. It is not used by the production application. Node 24 remains the repository requirement.

## Using the workspace

- **Tasks first:** Academic Tasks and Quick To-dos are immediate peer panels, with approximately 62%/38% columns at a content width of at least 860px. Container queries measure the space remaining after the sidebar and page padding. Narrower areas stack Academic Tasks first. Panels size to their contents and use normal page scrolling, rather than nested list scrollbars.
- **Default All:** the existing All semantics operate on the selected semester's scoped Tasks, including standalone Tasks. No saved task-view preference previously existed. All is the initial/fallback view; filter/search state persists while the workspace remains mounted and is not reset by data refresh or list expansion. A new page load starts at All. Today, Tomorrow, This Week, Upcoming, Overdue, Completed, By Subject and By Assignment retain their previous predicates/grouping.
- **Six at a time:** each primary list initially displays up to six outstanding items. Show more reveals six additional items in the same panel; Show less returns to six. Both new and old rows have direct editing controls. Records are never duplicated or moved to a second list store. Header counts show all outstanding academic Tasks in the selected scope and all pending personal To-dos, rather than only visible/search-matched rows.
- **Completed:** All places completed academic Tasks in a collapsed Completed section. Completed filter explicitly displays those records; date/group views keep their existing outstanding-only behaviour. Quick To-dos have a matching collapsed section. Expand to review/reopen and use the same more/less controls. Completion changes only status, not record existence or estimate-based assignment calculations.
- **Quick Task edit:** Edit expands name, optional due date/time, priority, status and estimated Hours/Minutes inside its row. An untouched fractional estimate is preserved exactly; changing duration recombines whole Hours and Minutes (fractional minutes remain allowed by the existing estimate model), with the existing 10000-hour bound. Existing due time, relationships, actual hours and notes are preserved unless the relevant editable value is explicitly changed. More details retains the full Task editor for notes/relationships/advanced fields.
- **Quick To-do edit:** Edit expands just title and optional due date. Its checkbox stays outside the editor. An acknowledged checkbox change made while editing updates only that editor's own revision; other-device edits still trigger a conflict. Existing ordering and completion status remain authoritative.
- **One quick editor:** one Task or To-do editor is open at a time across the workspace. Switching editors, hiding a draft by changing filter/search/Show less or opening a full editor asks before discarding unsaved edits. Save uses the original revision. Cancel/Escape discard local changes without writing. Failed saves retain the draft and show an error; cancel/reopen after a stale-edit conflict to load the latest version. Pending mutations disable competing actions. A Task's own checkbox is disabled while its quick editor is open because Status is editable there; otherwise completion/reopen is immediate.
- **Keyboard:** native forms provide Enter-to-add/save from appropriate single-line inputs. Quick editors contain no multiline fields; advanced notes stay in the existing full editor. Escape cancels quick editing when a save is not pending; Tab/Shift+Tab remain normal. Edit/menu targets are at least 44px, checkboxes have labelled hit areas and the existing visible focus rings remain.
- **Less noise:** checkbox, title and Edit stay visible. The labelled ellipsis menu contains Task Start Focus, More details and confirmed Delete; To-dos retain Convert to Task, Move up/down and confirmed Delete. Menus focus the first enabled item, support arrows/Home/End/Escape, close on outside interaction/blur and return focus to their trigger on dismissal. To-do moves retain the existing full ordering, including completed items. Convert to Task keeps V2.2's atomic creation/removal and retry safety.
- **Recurring Tasks:** collapsed at the bottom with an enabled-series count. Expand for the existing series, creation/editing and confirmed deletion. Completed/generated occurrences remain ordinary Tasks. No scheduler changes are made.
- **Assignment created:** a centred, narrower prompt labels the actual saved assignment name and aligns Maybe later / Break into tasks. Neither choice deletes the assignment.
- **Breakdown:** consistent header, labelled assignment, optional template controls, editable/reorderable task rows and a footer separate from the scrolling body. Long assignment names scroll with the body, so they cannot push the footer out. The progress notice is quieter; accessible help retains manual-progress, zero-estimate weighting and Submitted=100% information. Save stays disabled without valid selected tasks. Four templates, unsaved selection/editing/reordering, pending draft storage and atomic same-batch retries remain intact.

## Before updating

Use **Command Prompt**, not PowerShell, and run commands individually. These instructions assume `C:\Projects\student-dashboard` and task `Student Dashboard`. Finish/save an active study session if practical and close other clients during maintenance. Export fresh JSON while the app is running. Keep backups private and outside Git. Use the existing Node 24 installation required by the repository. No data restore is part of a normal update.

## A. Backup before update

1. While the application is still running, open **Settings → Semesters & data maintenance → Backups & data export → Export JSON backup**. Save this fresh export in your Downloads folder as `student-dashboard-before-v2.2.1.json`. If that name already exists, retain the old export elsewhere and ensure this path refers to the new export, not an earlier download.
2. Disable automatic startup and gracefully stop the dashboard:

```bat
cd /d "C:\Projects\student-dashboard"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
```

Continue only when the launcher reports Stopped and port 3000 is free. Disabling the task alone does not stop the application. Close other browser clients for maintenance.

3. Create a dated full backup outside the repository. Keep this Command Prompt open: later commands use its `SD_BACKUP` variable. The timestamp prevents overwriting an earlier backup. `%I` below is for an interactive Command Prompt, not a batch file.

```bat
for /f %I in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd-HHmmss"') do set "SD_BACKUP=C:\StudentDashboardBackups\%I-before-v2.2.1"
mkdir "%SD_BACKUP%"
copy /B "%USERPROFILE%\Downloads\student-dashboard-before-v2.2.1.json" "%SD_BACKUP%\portable.json"
robocopy "data" "%SD_BACKUP%\data" /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ
copy /B ".env" "%SD_BACKUP%\.env"
echo %SD_BACKUP%
npm run db:backup
```

For example, the folder might be `C:\StudentDashboardBackups\2026-10-11-093000-before-v2.2.1`. Write down the **actual folder printed**. Robocopy exit codes 0–7 are successful/non-fatal; 8 or higher means failure. Check its summary has zero failed files. `copy` must report one file copied for each file. The `data` copy includes `student.db`, any SQLite sidecars and other local runtime files. The extra `npm run db:backup` JSON is saved in `C:\Projects\student-dashboard\backups`; it does not replace the external backup. Keep these files private because the full copy contains authentication and push credentials.

## B. Verify before pulling

```bat
node -e "const fs=require('node:fs'),p=require('node:path'),b=process.env.SD_BACKUP,j=JSON.parse(fs.readFileSync(p.join(b,'portable.json'),'utf8'));if(j.format!=='student-dashboard'||![1,2].includes(j.version)||!Array.isArray(j.data.task))throw Error('Invalid backup');console.log('JSON readable:',j.data.semester.length,'semesters,',j.data.subject.length,'subjects,',j.data.task.length,'tasks,',j.data.assignment.length,'assignments,',j.data.exam.length,'exams,',j.data.studySession.length,'study sessions');for(const f of ['data/student.db','.env'])if(!fs.statSync(p.join(b,f)).size)throw Error('Empty backup file: '+f);console.log('Database and environment copies exist and are non-empty');"
```

Confirm the counts match the records you expect, the files have non-zero sizes and the extra local JSON has today's timestamp. Verify every copied data file and `.env` against the stopped originals without printing their contents:

```bat
powershell -NoProfile -Command "$ErrorActionPreference='Stop'; $src=Join-Path (Get-Location) 'data'; Get-ChildItem -LiteralPath $src -File -Recurse | ForEach-Object { $dest=Join-Path ($env:SD_BACKUP+'\data') $_.FullName.Substring($src.Length+1); if ((Get-FileHash -LiteralPath $_.FullName).Hash -ne (Get-FileHash -LiteralPath $dest).Hash) { throw 'Data copy mismatch' } }; if ((Get-FileHash -LiteralPath '.env').Hash -ne (Get-FileHash -LiteralPath ($env:SD_BACKUP+'\.env')).Hash) { throw 'Environment copy mismatch' }; Write-Output 'Full backup verified'"
```

Do not pull if verification fails. A parse/count check is not a restore rehearsal; retain both JSON and the complete stopped database copy.

## D. Recovery if records are missing

First check semester selection and filters. If a restore is needed, stop using the app on other devices and keep the scheduled task disabled. Restoring JSON **replaces academic/productivity records with the backup snapshot**, rather than merging them. Later edits will be replaced. The current data is backed up first and restore runs in a transaction. Existing passwords and sessions are not replaced by JSON.

### Restore through Settings when the app works

1. Keep the task disabled and run the dashboard manually using `node scripts/windows/dashboard.mjs start` from `C:\Projects\student-dashboard` if it is stopped. Do not start a second copy.
2. Sign in at `http://localhost:3000`.
3. Open **Settings → Semesters & data maintenance → Backups & data export → Restore a backup → Choose JSON backup**.
4. Select `portable.json` inside the **actual dated external backup folder** printed in step A, for example `C:\StudentDashboardBackups\2026-10-11-093000-before-v2.2.1\portable.json`.
5. Confirm replacement, wait for “Backup restored” and reload every open client. Verify records with All semesters and appropriate filters.
6. Only after verification, stop the manual app and enable/run the scheduled task using the commands in section C. The pre-restore JSON copy is in `C:\Projects\student-dashboard\backups`.

### Restore JSON through CLI

In a new Command Prompt, set `SD_BACKUP` to the actual backup folder you wrote down (replace the example timestamp). Do not continue while the app or port 3000 is active:

```bat
cd /d "C:\Projects\student-dashboard"
set "SD_BACKUP=C:\StudentDashboardBackups\2026-10-11-093000-before-v2.2.1"
schtasks /Change /TN "Student Dashboard" /Disable

```

Wait for “Backup restored. Previous data saved in backups/.” before starting. Verify records in the browser, then stop and enable/run the task as in section C. The CLI uses the same validation, transaction and automatic pre-restore backup as Settings. If the database is damaged so that JSON restore cannot read/back up its current contents, use the full-copy recovery below.

## E. Recovery if the database or application is damaged

Use this only with a verified full backup. It restores the entire database, credentials and local runtime state at the backup time. Keep the old damaged files for investigation; do not merge an old `student.db` with newer SQLite WAL/SHM files.

1. Stop the dashboard and verify port 3000 is free:

```bat
cd /d "C:\Projects\student-dashboard"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
```

If the launcher cannot confirm a safe stop/free port, do not copy a database over a running process. Resolve that failure first.

2. Select the actual full backup folder, check it exists and create a separate dated holding folder for the current state:

```bat
set "SD_BACKUP=C:\StudentDashboardBackups\2026-10-11-093000-before-v2.2.1"
dir /a "%SD_BACKUP%\data\student.db"
dir /a "%SD_BACKUP%\.env"
for /f %I in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd-HHmmss"') do set "SD_HOLD=C:\StudentDashboardBackups\%I-before-recovery"
mkdir "%SD_HOLD%"
if exist "data" move "data" "%SD_HOLD%\data"
if exist ".env" move ".env" "%SD_HOLD%\.env"
```

Continue only if the old `data` directory and `.env` were moved successfully (or did not exist). The target `C:\Projects\student-dashboard\data` must not exist before the copy below. This avoids mixing database generations.

3. Restore the complete directory and environment file:

```bat
robocopy "%SD_BACKUP%\data" "data" /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ
copy /B "%SD_BACKUP%\.env" ".env"
dir /a "data\student.db"
dir /a ".env"
```

Check zero failed files in the Robocopy summary and one environment file copied. Re-run the hash verification command from section B: it now compares the restored files against the backup. Do not touch `backups`, and do not run seed/reset/destructive Prisma commands.

4. Repair installed dependencies/build if needed, then validate and start:

```bat
npm install
npm test
npm run typecheck
npm run build
node --import tsx --test tests/startup-production.integration.ts
node scripts/windows/dashboard.mjs start
```

Sign in with the password valid at the full-backup time and verify your records. Use a second terminal for status/logs. Only then stop the manual app and enable/run the scheduled task as in section C. Keep `SD_HOLD` and the original backup until recovery is confirmed. Keep the V2.2.1 source. The V2.2 backup has the same schema; V2.2.1 adds no migration. Existing checked-in migrations still run safely if restoring a much older snapshot. Do not downgrade source as a recovery step.

## Physical acceptance checklist

First reload each browser/PWA, verify your existing subjects, assignments, Tasks, To-dos, exams and study history, and check localhost, LAN and the existing private Tailscale URL. Choose All semesters/appropriate filters when comparing record counts.

- Desktop: expanded/collapsed sidebar, short laptop screen, Comfortable/Compact density and light/dark mode. Academic Tasks must appear before Quick To-dos, with Recurring Tasks collapsed below. Wide content uses approximately 62%/38%; narrow content stacks without horizontal scrolling. Empty panels must not stretch to fill height.
- iPad: portrait/landscape, expanded/collapsed sidebar, browser and installed PWA. Verify the layout reacts to remaining content width, not only device width. Inline fields, menus and dialog buttons must remain readable/tappable.
- Phone: portrait/landscape, safe areas, navigation and keyboard. Edit only on an explicit tap. Task/To-do lists use page scrolling. Assignment breakdown has one scrolling body with a reachable footer; verify Save/Cancel with the keyboard open. No horizontal overflow or trapped scrolling.
- Confirm initial All; use every existing date/group/Completed view, search and semester selection. Show more/less in both panels must preserve filter/search and allow editing newly revealed rows. Complete/reopen through checkboxes; check the same record and linked progress on Today/Details and another device after refresh.
- Task edit: change title, due date/time, priority, Hours/Minutes and status. Check original notes, subject/assignment links and actual hours remain. More details opens the full editor. Try invalid values and Cancel/Escape; they must not alter records. Save a conflicting change from another device and verify the old draft is retained with a conflict message, then cancel/reopen.

Confirm title/date editing, checkbox completion while editing, completed-section reopening, menu ordering and declined/confirmed deletion. - Create an assignment and choose Maybe later; it must remain saved without Tasks. Create another and choose Break into tasks. Inspect actual name/spacing/button alignment. - Semester Progress retains `QUT Y1S2 | Week 11 of 13`, shared special states/resumption and the unchanged Dashboard date/week header.
- After restoring Task Scheduler operation, perform your real reboot and private remote-access check if desired. The launcher, Tailscale Run unattended and Serve --bg are unchanged.

## Validation scope

Automated React DOM interaction tests use jsdom and disposable SQLite, and exercise actual components/events with the existing service mutations. They cover layout order/default All, semester-scoped input, filters/search, list expansion, completed/recurring toggles, single-editor switching, Save/Cancel/Escape, failed/stale drafts, completion/progress, menu keyboard/actions, To-do ordering/conversion and assignment-created/breakdown flows. Enter uses standard native form submission; jsdom does not emulate the browser's full keyboard default actions. Existing V2.2 transactional retry, conversion rollback, backup/restore and all other regressions remain. Production CSS verification checks emitted container/layout/editor/modal rules. The separate production integration test runs a built server and safe lifecycle against disposable data.

No local browser binary is installed and the cloud browser cannot reach this workspace server. jsdom has no layout engine or genuine touch/virtual-keyboard environment. CSS/DOM tests do not establish physical responsive, Acer/iPad/phone/PWA, Windows Task Scheduler or reboot success. Perform the checklist above locally; no physical success is claimed.
