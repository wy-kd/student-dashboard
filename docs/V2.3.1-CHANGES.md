# V2.3.1 implementation checkpoints

Baseline: V2.3 `04b95355761f309d87817d954fcc393b91d19e52`.

## Stage 1 — Date-specific availability persistence

The V2.3 full-profile database mutation persists exceptions correctly, including multiple periods, all-day unavailability, replacement and returning to the weekly rule. Its focused integration and UI tests passed before changes. No server-side loss was reproduced.

The reproducible workflow defect was that **Add exception changed only local draft state**. The only persistence action was Save availability after the seven-day editor and preferences. Leaving Settings before that action discarded the new exception; no nearby controls communicated that it was unsaved. The original form also treated a newly added empty exception as unavailable without asking which of three states the user intended.

A dedicated date editor now offers Available at specific times, Unavailable all day and Use normal weekly schedule, a local Save date change button, explicit unsaved/saved feedback, Australian long-date labels and a chronological saved list. The `availability.exception` mutation changes only the selected date in a transaction, reuses the existing validation and guards the existing profile revision. Other persisted dates, weekly periods and preferences are untouched. Unsaved weekly browser changes remain in their draft. Failed and conflicting saves retain date input and periods. A successful save advances the browser revision and reconciles that date in the full-profile draft, so a later weekly save cannot overwrite it.

Automated acceptance covers save → reread database → capacity → edit/save again → unavailable → weekly reset, invalid dates/overlaps, stale rejection and failure retaining input. UI coverage remounts Settings, verifies the saved exception and verifies unsaved weekly edits are not written by a date save. The live Acer database was not accessed. No migration is needed for this stage.

## Stage 2 — Compact availability settings

Seven summary rows replace the seven simultaneously expanded forms. Edit one weekday at a time, copy its hours to selected days, clear hours and explicitly save next to the draft. Dates have their own local save; session preferences have a separate save and explain target versus hard maximum. Maximum daily time is shown in hours and stored as minutes. Appointments remain separate from permission to study; existing classes/exams need no duplicate entry. Empty weekly configuration is explained separately from days unavailable within a configured weekly schedule. The existing model does not record a per-weekday “never edited” flag; no new state is invented.

Section mutations are transactional, profile-revision guarded and modify only selected weekdays or preferences. A reload-saved-settings action retains open drafts and lets the user explicitly review/retry after a cross-device conflict. Focused UI/database tests (11) and typecheck passed. No migration required.

## Stage 3 — Guided scheduling

The shared week/tomorrow/rest-of-today/custom workflow now chooses a period, shows readiness using the existing engine's free-capacity calculation, reviews date-grouped compact suggestions and explicitly confirms selected sessions. No availability produces a setup action. Session fields appear only on Edit. Summary counts/durations follow the selection and edits; invalid times give an actionable message. Missing estimates, genuine capacity shortfalls and passed deadlines are separate groups, with three initial examples and expansion for every remaining item. Unknown durations never acquire invented hours. Existing commitments, extra engine information, confirmed-session maintenance and disruption details use progressive disclosure. All disruption items remain reachable.

Approval/undo, fingerprint checks, request pinning after an interrupted response, actual-time recording and the scheduling algorithm are unchanged. Tests cover all three civil date ranges, missing availability, selection/editing, the confirm step, safe retry, cancel, grouped causes and existing timer/disruption/transaction protections. Focused tests and typecheck passed; no migration.

## Stage 4 — Quick Create

New Assignments/Exams show name, subject and date; new Academic Tasks show name, optional date and optional subject/assessment links. More options retains all advanced fields and original defaults. Full edit retains saved fields and opens advanced details. New Tasks no longer acquire an arbitrary deadline. Dirty close asks before discarding, submissions have a synchronous guard and interrupted create responses pin the original payload for retry. Exam creation extends the existing deterministic request-ID mechanism already used by Tasks and Assignments; no new schema is required. Optional assignment breakdown remains after successful creation.

Focused creation, V2.2/V2.2.1 regressions and typecheck passed. UI tests cover hidden advanced values, editable validation failures, frozen uncertain retries, saved edit fields and rejecting dirty close. Database tests prove Exam retries create one row and preserve defaults.

## Stage 5 — Quick Add and capture

The shared native-dialog surface provides explicit Capture to Inbox, Academic Task, To-do, Assignment and Exam actions; secondary record types remain available. Desktop uses a compact anchored surface and narrow screens use a viewport-sized surface with bounded scrolling. Native modal focus/Escape semantics are retained, and closing/switching an unfinished entry asks before discarding. Task creation from an assessment/subject retains context without navigating away. Direct To-do creation uses the existing To-do service and never creates an Academic Task.

Capture now has local saved/error states, whitespace rejection, an immediate submission guard and stable request IDs. Lost responses freeze the payload until a same-ID retry; persisted duplicate captures are prevented. Existing callers without request IDs remain supported. Focused UI, database and To-do regressions plus typecheck passed. No migration needed for this stage.

## Stage 6 — Inbox review and reminders

Inbox has actionable, snoozed, archived and processed groups, with a separate sidebar capture count. Review creates either an Academic Task or a Quick To-do; transaction/revision checks protect source data and a request receipt makes conversion retry idempotent. Original text and conversion provenance remain saved. Archive creates no work, snooze expires in the configured timezone and deleting a capture preserves created records. An assignment announcement opens the existing revision-guarded assignment editor with its current deadline: only explicit Save changes writes the user's proposal, and the source capture remains intact. No automatic parsing or deadline change is introduced.

One additive migration adds lifecycle/revision/provenance fields to InboxItem and an InboxReviewPreference table. Existing captures default to pending; all other tables remain untouched. Review reminders default Off, offer Daily/Weekly with local time/day, respect existing quiet hours and private push, use generic notification copy and persist outstanding-state/period deduplication. Unchanged outstanding captures are not repeatedly announced on subsequent days. Reconciliation follows the existing running-app notification infrastructure.

Portable V3 backups include the new table/fields; older V1/V2/V3 imports remain supported through missing-field defaults and an optional new table. Restore advances revisions and preserves credentials. A populated V2.3 migration fixture verifies every original column value, including availability, plans, history and authentication. Focused database/reminder/backup tests and UI tests (43 total) plus typecheck passed. No physical device tests performed.
