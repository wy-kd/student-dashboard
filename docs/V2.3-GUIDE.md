# V2.3 — Basic Time Management & Scheduling

This release adds optional local scheduling and balances the Tasks panels. One additive checked-in migration, `20261011060000_v23_planning`, creates seven new tables and indexes; it does not alter, seed or rewrite existing tables. No dependency is added. Authentication, reminders, Web Push, recurring Tasks, To-dos, Windows startup, Task Scheduler and Tailscale configuration remain unchanged. SQLite remains at `data/student.db`.

## Using scheduling

1. In **Settings → Availability**, enter the periods when you are willing to study. Add multiple periods per day, copy a day, or leave it unavailable. Date exceptions replace that day's weekly periods; an empty exception means unavailable. Remove an exception to return to the weekly rule. Overnight availability is entered as two periods on adjacent days. Preferences control session lengths, rest and optional maximum daily study; **Daily study target** remains a goal, not proof of availability.
2. Record appointments under Availability's commitments. Fixed and flexible appointments both reserve time; the scheduler never moves them. Existing classes, exams and legacy uncompleted study plans also reserve time. Semester Break suppresses classes through the existing calculation. Deadlines and informational dates do not consume availability.
3. In **Today** or **Study**, choose **Plan my week**, **Plan tomorrow**, **Plan remainder of today** or a custom period of up to 14 days. Existing unfinished Tasks and unlinked assignments/exams are reused. Linked Tasks replace their parent workload, with estimate differences explained. Semester selection scopes proposed academic work; all physical commitments still reserve time.
4. Supply explicit remaining minutes for unestimated or partly recorded work. The planner does not guess one hour, infer completed work from planned time or subtract timer minutes to manufacture an exact remaining estimate. It considers the earliest Task/assessment deadline, priorities, availability, rest, session lengths and daily limits. Unknown durations, deadline-specific shortfalls and conflicts are explained. No past or late blocks are suggested.
5. Review the **unconfirmed** preview. Edit times/duration, title and linked work; deselect/remove blocks, exclude work, reserve extra study time, regenerate or cancel. An explicit manual availability override still obeys deadlines, occupied time and daily limits. Preview is limited to 200 blocks. **Accept selected changes** rechecks current records inside a transaction; changes made on another device require a fresh review. It creates only intentions, never Task completion or actual StudySessions.
6. Confirmed work appears in Today, Calendar, Timetable, Study and assessment details. Today separates intended hours, actual recorded hours, future confirmed allocation and remaining known availability from the daily target. Scheduled/due Tasks appear once. Calendar selection opens the plan's original context. **Edit / reschedule** requires approval; fixed sessions must first be explicitly unlocked.
7. **Start planned session** starts the existing synchronised timer with its Task/assessment and intended duration. The lifecycle remains Start → Pause/Resume → End → Review → Save/Discard. A timer save records actual time once, preserving intended time separately (for example 60 intended and 35 recorded minutes). Tasks complete only through an explicit existing completion action. The existing countdown limit is 240 minutes; longer manual reservations start a 240-minute segment and retain the full intention separately.
8. Recorded appointments, exceptions, deadline changes, reassociated/completed work, changed daily limits and elapsed unconfirmed plans produce review prompts. **Review alternative times** proposes one existing reservation's move at a time; approval updates that same block. All other plans remain protected. **Keep current plan** writes nothing and hides that prompt for the current mounted page; it can return on reopening or changed facts. **Dismiss** explicitly hides the intention, preserving academic work/history. **Record what I completed** opens an explicit manual actual-work review; active timers use their own End/review flow. No missed session is automatically considered failed work.

Approval retries retain the same UUID and exact request after an interrupted response. Retry that request before changing its draft. After a full reload, inspect confirmed work before generating again. Recent approval history supports **Undo approval** only while affected blocks are unchanged, unrecorded and without active timers; restoring moved slots also checks current conflicts. Restored backups retain batch history but invalidate old undo baselines. Fixed commitments and historical StudySessions are never removed by undo.

Portable JSON is now version **3**, including every new scheduling table. V1/V2 import remains supported; restoring an older snapshot clears later scheduling intentions rather than leaving dangling plans. JSON restore replaces academic/productivity/scheduling state, preserves existing password/sessions and saves a pre-restore JSON backup. Existing CSV exports remain available for academic tables; JSON is the round-trip format. Legacy forecast/health widgets retain their original target-based heuristics and are separate from exact availability-aware proposals.

## Backup-first Acer update

Use **Windows Command Prompt**, not PowerShell, and run each command individually. The paths below use your existing `C:\Projects\student-dashboard` and scheduled task `Student Dashboard`. Keep the same Command Prompt open for its backup variables. `%I` is interactive CMD syntax; a batch file would require `%%I`. Finish/review an active timer if practical and close other clients during maintenance. Retain every backup; none of these commands resets or seeds data.

### 1. Export JSON while the current app is running

Open **Settings → Semesters & data maintenance → Backups & data export → Export JSON backup**. Save the fresh export in Downloads as `student-dashboard-before-v2.3.json`. Ensure this is the new export, rather than an older file with the same name. JSON contains private academic information and is unencrypted.

### 2. Disable startup and stop safely

```bat
cd /d "C:\Projects\student-dashboard"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
```

Continue only when the dashboard is stopped **and port 3000 is free**. Disabling the task alone does not stop the server. If a port owner cannot be identified/stopped safely, resolve it before copying or updating data. Leave Tailscale configuration as it is.

### 3. Create a complete timestamped external backup

Create the extra application JSON first, while stopped, then copy the full directory so any SQLite read/checkpoint activity finishes before the full-copy hash baseline. No source update or migration is run in this step.

```bat
npm run db:backup
for /f %I in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd-HHmmss"') do set "SD_BACKUP=C:\StudentDashboardBackups\%I-before-v2.3"
mkdir "%SD_BACKUP%"
git rev-parse HEAD > "%SD_BACKUP%\source.txt"
copy /B "%USERPROFILE%\Downloads\student-dashboard-before-v2.3.json" "%SD_BACKUP%\portable.json"
robocopy "data" "%SD_BACKUP%\data" /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ
copy /B ".env" "%SD_BACKUP%\.env"
echo %SD_BACKUP%
```

Write down the actual folder printed. Check **zero failed files** in Robocopy's summary (exit codes 0–7 are non-fatal; 8+ is failure). Each `copy` must report one file copied. Back up the **entire stopped `data` directory**, including SQLite sidecars and local runtime files. The external `.env` and full database contain authentication/push secrets: keep them private and outside Git. Existing `backups/` stays untouched; optionally copy it to another drive too. The extra `db:backup` JSON is in `backups/` and does not replace the external full copy.

### 4. Verify sizes, counts and every copied file

```bat

dir /a "%SD_BACKUP%\.env"

```

Compare counts with your expected semesters, subjects, assignments, Tasks, exams, study history and To-dos. Check the extra local JSON has the timestamp from step 3. These commands print counts/success, not private record contents, hashes or secrets. **Stop if any verification fails.** Parsing and hashes do not substitute for a restore rehearsal; keep both portable JSON and the full copy.

## Recovery

Keep automatic startup disabled throughout recovery. Preserve later data separately before replacement. No recovery procedure merges database files or uses seed/reset/destructive Prisma commands. Choose recovery deliberately; a normal update does not restore a snapshot.

### A. Portable JSON recovery

JSON replaces later academic/productivity/scheduling edits with the snapshot; it is not a merge. Current password/sessions stay intact. V1/V2 imports do not contain V2.3 scheduling and clear later plans/settings. Invalid imports roll back; the current contents are backed up first.

If the application works, run it manually with the task disabled, sign in at localhost and use **Settings → Semesters & data maintenance → Backups & data export → Restore a backup → Choose JSON backup**. Select `portable.json` from the actual external folder, confirm replacement, wait for **Backup restored**, then reload every client and verify records. Stop the manual app and re-enable/run Task Scheduler only after verification.

For CLI restore, substitute your actual dated folder; first confirm stopped/free port:

```bat
cd /d "C:\Projects\student-dashboard"
set "SD_BACKUP=C:\StudentDashboardBackups\YOUR-ACTUAL-TIMESTAMP-before-v2.3"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
dir /a "%SD_BACKUP%\portable.json"
npm run db:backup -- "%SD_BACKUP%\portable.json" --confirm
node scripts/windows/dashboard.mjs start
```

Wait for the successful restore message before starting. This uses the same validation, transaction and pre-restore backup as Settings. If the current database is too damaged to read/back up, use full SQLite recovery instead. Retain `backups/` and the external original.

### B. Full SQLite recovery while keeping V2.3 source

This restores the full local database/credentials/runtime state at backup time. Keep the current V2.3 source so its compatible additive migration can be deployed. Stop and confirm free port as above, then choose the verified backup and move current files aside:

```bat
set "SD_BACKUP=C:\StudentDashboardBackups\YOUR-ACTUAL-TIMESTAMP-before-v2.3"
dir /a "%SD_BACKUP%\data\student.db"
dir /a "%SD_BACKUP%\.env"
for /f %I in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd-HHmmss"') do set "SD_HOLD=C:\StudentDashboardBackups\%I-before-recovery"
mkdir "%SD_HOLD%"
if exist "data" move "data" "%SD_HOLD%\data"
if exist ".env" move ".env" "%SD_HOLD%\.env"
```

Continue only if moves succeeded (or files did not exist) and the repository's `data` directory is absent. Never overlay an old database on new WAL/SHM/journal sidecars.

```bat
robocopy "%SD_BACKUP%\data" "data" /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ
copy /B "%SD_BACKUP%\.env" ".env"
dir /a "data\student.db"
dir /a ".env"
```

Check zero failed files and a successful environment copy. Re-run the size/hash verification from update step 4, now comparing the restored directory with the backup. Retain `SD_HOLD`, the original snapshot and `backups/`. Then:

```bat
npm install
npm test
npm run typecheck
npm run build
node --import tsx --test tests/startup-production.integration.ts
node scripts/windows/dashboard.mjs start
```

Install safely deploys V2.3's checked-in migrations to an older compatible snapshot. Sign in with the password valid at backup time, verify records, and only then stop/enable/run scheduled operation using update step 6.

### C. Failed migration or actual rollback to the previous release

If installation/migration fails, keep the task disabled and server stopped. Preserve the failing directory and environment with the holding-folder procedure above. Review diagnostics; do not reset the database, delete migration history or mark migrations applied without diagnosis. A Git revert alone **does not roll back SQLite schema or records**.

For an actual rollback, use the **matching pre-update source checkpoint and complete verified pre-update data snapshot together**. Follow recovery B to move the failed/current files aside and copy the full pre-update `data` and `.env`, then verify hashes. Before installing, select the old source recorded before the update:

```bat
git status --short
for /f "usebackq delims=" %I in ("%SD_BACKUP%\source.txt") do set "SD_SOURCE=%I"
git switch --detach "%SD_SOURCE%"
git rev-parse HEAD
npm ci
npm test
npm run typecheck
npm run build
node --import tsx --test tests/startup-production.integration.ts
node scripts/windows/dashboard.mjs start
```

Do not switch with unexplained tracked changes; preserve them first. Confirm the selected hash matches `source.txt`. Detaching selects the matching old source without erasing main or backups. Its checked-in migrations run against the restored old snapshot; the failed/new database remains in `SD_HOLD`. This loses later changes from the active copy, including new scheduling, so retain that held copy for investigation or recovery under compatible newer code. Verify records before re-enabling the task. Never run old code against a failed/new schema as a substitute for this paired restoration.

To retry V2.3 later, stop/disable again, make another verified backup of the recovered state, use `git switch main` and `git pull --ff-only`, then follow the install/validation/build/start steps. Keep the original backups until recovery and physical checks are complete.

## Physical acceptance checklist

- Desktop: expanded/collapsed sidebar, short laptop screen, Comfortable/Compact density and light/dark mode. Tasks panels stretch equally side-by-side at wide content widths, use matching responsive minimum heights when empty, grow naturally and stack on narrower content. Lists scroll with the page; every item/CTA stays reachable.
- iPad: portrait/landscape, browser/PWA and both sidebar states. Planning fields/cards, Calendar events and dialogs remain readable/tappable without horizontal overflow. Check long names and keyboard-open dialogs; review bodies scroll and footer actions remain reachable.
- Phone: portrait/landscape, navigation, timer float, safe areas and virtual keyboard. Weekly availability, exceptions, preview edits and actual-work review have labelled controls/44px actions and normal scrolling. Long titles wrap.
- Existing records: subjects, assignments, Tasks, To-dos, recurring series, exams, history/totals, reminders and push continue to work. Compare counts in All semesters with filters cleared. Verify assignment breakdown/templates and completion/reopening.
- Scheduling: multiple periods, copy/unavailable/exception/reset; normal classes and Semester Break; unknown remaining estimates; exact Task/parent due time; preview without writes; selective acceptance and safe stale-device rejection; manual override with fixed commitments protected; undo without erasing newer edits/history.
- Integration: Today shows intentions separately from actuals and each Task once. Calendar/Timetable show one event per confirmed plan; source links work. Start → Pause/Resume on another device → End/review → save once and discard another. Check intended 60 versus recorded 35 minutes and explicit remaining estimates.
- Disruption: record an overlapping appointment or exception; verify an unsaved alternative and unchanged current plan before approval. Keep/Cancel preserve it. Completed/reassociated work requires review. Past unconfirmed sessions remain neutral and allow record/keep/dismiss.
- Infrastructure: localhost, LAN and existing private Tailscale HTTPS; PWA reload and push. After re-enabling Task Scheduler, verify a full reboot locally. No Funnel/public exposure/router rules are introduced.

Automated validation uses disposable SQLite and React DOM/jsdom, interval/DST tests, migration preservation, V3/older backup imports, emitted production CSS and the built-server lifecycle. It does not establish real touch/layout/virtual-keyboard, Acer/iPad/phone, Task Scheduler or reboot success. No local browser binary is available in this environment; physical checks remain yours.
