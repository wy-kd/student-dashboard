# V2.3.1 — Scheduling UX, Quick Create, Inbox and navigation

Baseline: V2.3 `04b95355761f309d87817d954fcc393b91d19e52`. Nine sequential commits implement and validate this correction release. See [the stage/change record](V2.3.1-CHANGES.md) for the diagnosed cause, services reused and validation boundaries.

## Availability that clearly saves

V2.3's database save was working in the reproduced cases. **Add exception** only changed local form state, with persistence hidden behind the distant whole-profile Save button; leaving Settings lost that draft. No server-side loss was reproduced. V2.3.1 fixes that workflow and tests database rereads and scheduling capacity.

- **Weekly availability:** Seven compact saved summaries. Edit one day, add multiple periods, copy to chosen days or clear hours, then **Save weekly hours** beside the draft. Only those days change. Days without hours have no capacity; a new profile says No hours set, while a saved profile says Unavailable. The old model has no separate per-day never-edited flag.
- **Date-specific changes:** Select a date shown in Australian long-date form. Choose Available at specific times, Unavailable all day or Use normal weekly schedule. **Save date change** persists only that date. Saved changes are chronological. Edit reopens them; Remove date change prepares a weekly-rule reset which still requires Save. No confirmed plan moves automatically.
- **Study session preferences:** Independent save for preferred/minimum minutes, rest minutes and optional maximum daily hours. Maximum is a hard limit; the daily study target is a goal.
- **Commitments:** Classes/exams are included automatically. Other appointments reserve time; both fixed/flexible commitments remain reserved until explicitly edited.

Drafts and errors stay near their controls. A save updates only its section, protecting other unsaved sections. Cross-device conflicts are rejected. **Reload saved settings** refreshes the revision while retaining open drafts; review those drafts before explicitly retrying. A successful save says which date/day was saved. An acknowledged write followed by a failed page refresh says it was saved, rather than falsely claiming loss.

## Planning without an overwhelming form

1. Choose **Plan my week** (today plus six days), **Plan tomorrow**, **Plan the rest of today**, or secondary custom dates (up to 14 days). The configured timezone determines civil dates. Read the capacity/reservation/missing-estimate summary. Missing availability provides **Set availability**.
2. **Suggest study sessions** produces an unsaved preview. Suggestions are grouped by date, showing work, times, duration and selection. **Edit session** expands detailed fields. Existing reservations and secondary engine information stay available in collapsed sections.
3. Review separate groups for missing estimates, insufficient capacity, passed deadlines and conflicts. Three initial examples keep lists short; Show all retains every other item. Set remaining time in place or review availability/deadlines. Reported unscheduled hours come from the engine; unknown work does not acquire invented duration.
4. **Review selected sessions**, then **Accept selected sessions**. The summary follows edits/selection. Cancel writes nothing. Regenerate does not change confirmed work. Acceptance creates intentions only; Task completion and actual study history stay separate. After acknowledgement, use Open Today or Open Calendar.

The existing engine, deadline/capacity/overlap checks, optimistic fingerprints, transactions, undo guards and duplicate StudySession protection remain intact. Missing estimates after recording work still require explicit user input. Linked Tasks replace their parent workload rather than double-counting it. Approvals, edits and actual-work recordings retain exact requests after interrupted responses: retry the same request before editing. After a full reload, inspect saved records before submitting another proposal. Manual overrides never bypass deadlines, reserved time or daily limits.

Disruption prompts and confirmed-session secondary actions use compact expansions. Every prompt stays reachable. An alternative is unsaved until approved; Keep/Cancel do not move a plan. Timer operation remains Pause/Resume → End → existing review/save/discard, including cross-device synchronisation and actual-time recording once.

## Quick Create and Quick Add

New Assignment/Exam dialogs show name, subject and date/time; Task creation shows name, optional date and optional context. More options keeps every advanced field/default. Existing record editing opens saved advanced values. Collapsing fields never discards them. Dirty close asks before discarding. After a lost create response, the original request is frozen for same-ID retry, including Exams. Assignment breakdown remains optional after creation.

Quick Add offers **Capture to Inbox**, **New Academic Task**, **New To-do**, **New Assignment**, **New Exam** and secondary record types. It keeps the current page; Task creation from an assessment/subject prefills its context. Direct To-do creation uses the existing To-do service. Capture uses one input, Enter to submit, clear saved/error states and stable IDs for retry. Empty/whitespace captures cannot be saved. Native dialog focus/Escape and explicit unfinished-entry confirmation are used.

## Inbox processing and optional reminders

The actionable Inbox count is distinct from unread notifications. Review can create a Task or a To-do, archive without creating work, delete with confirmation, or snooze until a configured-zone review time. Archived/processed and not-yet-due snoozed items do not inflate the immediate count. Original text and conversion provenance remain saved. Conversion is transactional/revision guarded; interrupted retries cannot create a second destination. Deleting the original capture preserves its created work.

For an announcement, select a related assignment, inspect its current deadline, then **Review and edit deadline** opens the existing editor. The user proposes the value and explicitly saves it with the existing revision guard. Cancelling or failed validation changes no assignment. The capture remains; nothing parses or updates deadlines automatically.

**Inbox review reminders** default Off. Explicitly choose Daily or Weekly, local time and weekly day. The existing running-server worker reconciles them about once per minute. Quiet hours defer reminders; existing private-push settings and delivery deduplication apply. The unchanged set of outstanding capture IDs/revisions is not repeatedly announced on later days. At most one reminder is created per selected day. Weekly reminders occur on the chosen day; a laptop that is off throughout that day waits until the next chosen day. Notification copy contains only a count, never capture text. No Google/Gmail integration or custom schedule is added.

## Navigation, database and compatibility

The workspace now lives in the shared Next.js layout. Sidebar DOM identity survives page changes, including Back/Forward. Its native scroll offset is saved per browser tab in sessionStorage, separately for desktop/mobile, and restored after refresh/collapse/expand. A shorter/new viewport clamps impossible offsets naturally. Hidden scrollbars still use overflow-y:auto; keyboard focus may naturally reveal a focused item. Storage failures leave navigation usable. No scroll preference is stored in SQLite.

One additive migration, `20261011090000_v231_inbox`, adds InboxItem lifecycle/revision/provenance columns and InboxReviewPreference. Existing captures become pending; academic, scheduling, history and credential values are unchanged. A populated V2.3 fixture checks every original column value after migration. SQLite stays in `data/student.db`; migrations run only through existing migrate deploy. No dependency, build-on-boot, launcher, Task Scheduler, Tailscale, authentication, timer architecture or external integration change is made.

Portable backups remain version 3 with additional Inbox fields/table. Current code imports older V1/V2/V3 backups. An older V2.3 application should not be used to restore a new V2.3.1 export: use compatible code or the paired old-source/full-data recovery below. Old versions do not know new Inbox fields. Credentials and sessions remain excluded from JSON and preserved by restore; a private stopped full data/.env copy preserves installation state. `.env`, data/, backups/ and logs remain excluded from Git.

## Backup-first Acer update

Use **Windows Command Prompt**, not PowerShell, and run each command individually. The paths below use your existing `C:\Projects\student-dashboard` and scheduled task `Student Dashboard`. Keep the same Command Prompt open for its backup variables. `%I` is interactive CMD syntax; a batch file would require `%%I`. Finish/review an active timer if practical and close other clients during maintenance. Retain every backup; none of these commands resets or seeds data.

### 1. Export JSON while the current app is running

Open **Settings → Semesters & data maintenance → Backups & data export → Export JSON backup**. Save the fresh export in Downloads as `student-dashboard-before-v2.3.1.json`. Ensure this is the new export, rather than an older file with the same name. JSON contains private academic information and is unencrypted.

### 2. Disable startup and stop safely

```bat
cd /d "C:\Projects\student-dashboard"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
```

Continue only when the dashboard is stopped **and port 3000 is free**. Disabling the task alone does not stop the server. If a port owner cannot be identified/stopped safely, resolve it before copying or updating data. Leave Tailscale configuration as it is.

### 3. Create a complete timestamped external backup

Create the extra application JSON first, while stopped, then copy the full directory so any SQLite read/checkpoint activity finishes before the full-copy hash baseline. No source update or migration is run in this step.

```bat
npm run db:backup
for /f %I in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd-HHmmss"') do set "SD_BACKUP=C:\StudentDashboardBackups\%I-before-v2.3.1"

git rev-parse HEAD > "%SD_BACKUP%\source.txt"
copy /B "%USERPROFILE%\Downloads\student-dashboard-before-v2.3.1.json" "%SD_BACKUP%\portable.json"
robocopy "data" "%SD_BACKUP%\data" /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ
copy /B ".env" "%SD_BACKUP%\.env"
echo %SD_BACKUP%
```

Write down the actual folder printed. Check **zero failed files** in Robocopy's summary (exit codes 0–7 are non-fatal; 8+ is failure). Each `copy` must report one file copied. Back up the **entire stopped `data` directory**, including SQLite sidecars and local runtime files. The external `.env` and full database contain authentication/push secrets: keep them private and outside Git. Existing `backups/` stays untouched; optionally copy it to another drive too. The extra `db:backup` JSON is in `backups/` and does not replace the external full copy.

## Recovery

Keep automatic startup disabled throughout recovery. Preserve later data separately before replacement. No recovery procedure merges database files or uses seed/reset/destructive Prisma commands. Choose recovery deliberately; a normal update does not restore a snapshot.

### A. Portable JSON recovery

JSON replaces later academic/productivity/scheduling edits with the snapshot; it is not a merge. Current password/sessions stay intact. V1/V2 imports do not contain scheduling and clear later plans/settings. Older V3 snapshots preserve their scheduling but restore captures as unprocessed and review reminders as Off when the new fields/table are absent. Invalid imports roll back; the current contents are backed up first.

If the application works, run it manually with the task disabled, sign in at localhost and use **Settings → Semesters & data maintenance → Backups & data export → Restore a backup → Choose JSON backup**. Select `portable.json` from the actual external folder, confirm replacement, wait for **Backup restored**, then reload every client and verify records. Stop the manual app and re-enable/run Task Scheduler only after verification.

For CLI restore, substitute your actual dated folder; first confirm stopped/free port:

```bat
cd /d "C:\Projects\student-dashboard"
set "SD_BACKUP=C:\StudentDashboardBackups\YOUR-ACTUAL-TIMESTAMP-before-v2.3.1"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
dir /a "%SD_BACKUP%\portable.json"
npm run db:backup -- "%SD_BACKUP%\portable.json" --confirm
node scripts/windows/dashboard.mjs start
```

Wait for the successful restore message before starting. This uses the same validation, transaction and pre-restore backup as Settings. If the current database is too damaged to read/back up, use full SQLite recovery instead. Retain `backups/` and the external original.

### B. Full SQLite recovery while keeping V2.3.1 source

This restores the full local database/credentials/runtime state at backup time. Keep the current V2.3.1 source so its compatible additive migration can be deployed. Stop and confirm free port as above, then choose the verified backup and move current files aside:

```bat
set "SD_BACKUP=C:\StudentDashboardBackups\YOUR-ACTUAL-TIMESTAMP-before-v2.3.1"
dir /a "%SD_BACKUP%\data\student.db"
dir /a "%SD_BACKUP%\.env"
for /f %I in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd-HHmmss"') do set "SD_HOLD=C:\StudentDashboardBackups\%I-before-recovery"
mkdir "%SD_HOLD%"
if exist "data" move "data" "%SD_HOLD%\data"
if exist ".env" move ".env" "%SD_HOLD%\.env"
```

Continue only if moves succeeded (or files did not exist) and the repository's `data` directory is absent. Never overlay an old database on new WAL/SHM/journal sidecars.

```bat
robocopy "%SD_BACKUP%\data" "data" /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ
copy /B "%SD_BACKUP%\.env" ".env"
dir /a "data\student.db"
dir /a ".env"
```

Check zero failed files and a successful environment copy. Re-run the size/hash verification from update step 4, now comparing the restored directory with the backup. Retain `SD_HOLD`, the original snapshot and `backups/`. Then:

```bat
npm install
npm test
npm run typecheck
npm run build
node --import tsx --test tests/startup-production.integration.ts
node scripts/windows/dashboard.mjs start
```

Install safely deploys V2.3.1's checked-in migrations to an older compatible snapshot. Sign in with the password valid at backup time, verify records, and only then stop/enable/run scheduled operation using update step 6.

### C. Failed migration or actual rollback to the previous release

If installation/migration fails, keep the task disabled and server stopped. Preserve the failing directory and environment with the holding-folder procedure above. Review diagnostics; do not reset the database, delete migration history or mark migrations applied without diagnosis. A Git revert alone **does not roll back SQLite schema or records**.

For an actual rollback, use the **matching pre-update source checkpoint and complete verified pre-update data snapshot together**. Follow recovery B to move the failed/current files aside and copy the full pre-update `data` and `.env`, then verify hashes. Before installing, select the old source recorded before the update:

```bat
git status --short
for /f "usebackq delims=" %I in ("%SD_BACKUP%\source.txt") do set "SD_SOURCE=%I"
git switch --detach "%SD_SOURCE%"
git rev-parse HEAD
npm ci
npm test
npm run typecheck
npm run build
node --import tsx --test tests/startup-production.integration.ts
node scripts/windows/dashboard.mjs start
```

Do not switch with unexplained tracked changes; preserve them first. Confirm the selected hash matches `source.txt`. Detaching selects the matching old source without erasing main or backups. Its checked-in migrations run against the restored old snapshot; the failed/new database remains in `SD_HOLD`. This loses later changes from the active copy, including new Inbox and scheduling, so retain that held copy for investigation or recovery under compatible newer code. Verify records before re-enabling the task. Never run old code against a failed/new schema as a substitute for this paired restoration.

To retry V2.3.1 later, stop/disable again, make another verified backup of the recovered state, use `git switch main` and `git pull --ff-only`, then follow the install/validation/build/start steps. Keep the original backups until recovery and physical checks are complete.
