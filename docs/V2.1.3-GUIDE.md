# V2.1.3: date cleanup, timer cancellation and personal to-dos

Your Acer now contains real university records. **Complete the backup and verification steps before pulling this release.** Run the commands individually in Command Prompt, not PowerShell, and stop if any step fails. These commands assume `C:\Projects\student-dashboard` and the existing scheduled task named `Student Dashboard`.

## A. Backup before update

1. While the application is still running, open **Settings → Semesters & data maintenance → Backups & data export → Export JSON backup**. Save this fresh export in your Downloads folder as `student-dashboard-before-v2.1.3.json`. If that name already exists, retain the old export elsewhere and ensure this path refers to the new export, not an earlier download.
2. Disable automatic startup and gracefully stop the dashboard:

```bat
cd /d "C:\Projects\student-dashboard"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
```

Continue only when the launcher reports Stopped and port 3000 is free. Disabling the task alone does not stop the application. Close other browser clients for maintenance.

3. Create a dated full backup outside the repository. Keep this Command Prompt open: later commands use its `SD_BACKUP` variable. The timestamp prevents overwriting an earlier backup. `%I` below is for an interactive Command Prompt, not a batch file.

```bat
for /f %I in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd-HHmmss"') do set "SD_BACKUP=C:\StudentDashboardBackups\%I-before-v2.1.3"
mkdir "%SD_BACKUP%"
copy /B "%USERPROFILE%\Downloads\student-dashboard-before-v2.1.3.json" "%SD_BACKUP%\portable.json"
robocopy "data" "%SD_BACKUP%\data" /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ
copy /B ".env" "%SD_BACKUP%\.env"
echo %SD_BACKUP%
npm run db:backup
```

For example, the folder might be `C:\StudentDashboardBackups\2026-09-08-153000-before-v2.1.3`. Write down the **actual folder printed**. Robocopy exit codes 0–7 are successful/non-fatal; 8 or higher means failure. Check its summary has zero failed files. `copy` must report one file copied for each file. The `data` copy includes `student.db`, any SQLite sidecars and other local runtime files. The extra `npm run db:backup` JSON is saved in `C:\Projects\student-dashboard\backups`; it does not replace the external backup. Keep these files private because the full copy contains authentication and push credentials.


Confirm the counts match the records you expect, the files have non-zero sizes and the extra local JSON has today's timestamp. Verify every copied data file and `.env` against the stopped originals without printing their contents:

```bat
powershell -NoProfile -Command "$ErrorActionPreference='Stop'; $src=Join-Path (Get-Location) 'data'; Get-ChildItem -LiteralPath $src -File -Recurse | ForEach-Object { $dest=Join-Path ($env:SD_BACKUP+'\data') $_.FullName.Substring($src.Length+1); if ((Get-FileHash -LiteralPath $_.FullName).Hash -ne (Get-FileHash -LiteralPath $dest).Hash) { throw 'Data copy mismatch' } }; if ((Get-FileHash -LiteralPath '.env').Hash -ne (Get-FileHash -LiteralPath ($env:SD_BACKUP+'\.env')).Hash) { throw 'Environment copy mismatch' }; Write-Output 'Full backup verified'"
```

Do not pull if verification fails. A parse/count check is not a restore rehearsal; retain both JSON and the complete stopped database copy.

## D. Recovery if records are missing

First check semester selection and filters. If a restore is needed, stop using the app on other devices and keep the scheduled task disabled. Restoring JSON **replaces academic/productivity records with the backup snapshot**, rather than merging them. Later edits will be replaced. The current data is backed up first and restore runs in a transaction. Existing passwords and sessions are not replaced by JSON.

### Restore through Settings when the app works

1. Keep the task disabled and run the dashboard manually using `node scripts/windows/dashboard.mjs start` from `C:\Projects\student-dashboard` if it is stopped. Do not start a second copy.
2. Sign in at `http://localhost:3000`.
3. Open **Settings → Semesters & data maintenance → Backups & data export → Restore a backup → Choose JSON backup**.
4. Select `portable.json` inside the **actual dated external backup folder** printed in step A, for example `C:\StudentDashboardBackups\2026-09-08-153000-before-v2.1.3\portable.json`.
5. Confirm replacement, wait for “Backup restored” and reload every open client. Verify records with All semesters and appropriate filters.
6. Only after verification, stop the manual app and enable/run the scheduled task using the commands in section C. The pre-restore JSON copy is in `C:\Projects\student-dashboard\backups`.

### Restore JSON through CLI

In a new Command Prompt, set `SD_BACKUP` to the actual backup folder you wrote down (replace the example timestamp). Do not continue while the app or port 3000 is active:

```bat
cd /d "C:\Projects\student-dashboard"
set "SD_BACKUP=C:\StudentDashboardBackups\2026-09-08-153000-before-v2.1.3"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
dir /a "%SD_BACKUP%\portable.json"
npm run db:backup -- "%SD_BACKUP%\portable.json" --confirm
node scripts/windows/dashboard.mjs start
```

Wait for “Backup restored. Previous data saved in backups/.” before starting. Verify records in the browser, then stop and enable/run the task as in section C. The CLI uses the same validation, transaction and automatic pre-restore backup as Settings. If the database is damaged so that JSON restore cannot read/back up its current contents, use the full-copy recovery below.

## E. Recovery if the database or application is damaged

Use this only with a verified full backup. It restores the entire database, credentials and local runtime state at the backup time. Keep the old damaged files for investigation; do not merge an old `student.db` with newer SQLite WAL/SHM files.

1. Stop the dashboard and verify port 3000 is free:

```bat
cd /d "C:\Projects\student-dashboard"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
```

If the launcher cannot confirm a safe stop/free port, do not copy a database over a running process. Resolve that failure first.

2. Select the actual full backup folder, check it exists and create a separate dated holding folder for the current state:

```bat
set "SD_BACKUP=C:\StudentDashboardBackups\2026-09-08-153000-before-v2.1.3"
dir /a "%SD_BACKUP%\data\student.db"
dir /a "%SD_BACKUP%\.env"
for /f %I in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd-HHmmss"') do set "SD_HOLD=C:\StudentDashboardBackups\%I-before-recovery"
mkdir "%SD_HOLD%"
if exist "data" move "data" "%SD_HOLD%\data"
if exist ".env" move ".env" "%SD_HOLD%\.env"
```

Continue only if the old `data` directory and `.env` were moved successfully (or did not exist). The target `C:\Projects\student-dashboard\data` must not exist before the copy below. This avoids mixing database generations.

3. Restore the complete directory and environment file:

```bat
robocopy "%SD_BACKUP%\data" "data" /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ
copy /B "%SD_BACKUP%\.env" ".env"
dir /a "data\student.db"
dir /a ".env"
```

Check zero failed files in the Robocopy summary and one environment file copied. Re-run the hash verification command from section B: it now compares the restored files against the backup. Do not touch `backups`, and do not run seed/reset/destructive Prisma commands.

4. Repair installed dependencies/build if needed, then validate and start:

```bat
npm install
npm test
npm run typecheck
npm run build
node --import tsx --test tests/startup-production.integration.ts
node scripts/windows/dashboard.mjs start
```

Sign in with the password valid at the full-backup time and verify your records. Use a second terminal for status/logs. Only then stop the manual app and enable/run the scheduled task as in section C. Keep `SD_HOLD` and the original backup until recovery is confirmed. Keep the V2.1.3 source. After restoring a pre-V2.1.3 full database copy, `npm install` reapplies the additive To-do migration through the existing migration runner. That old snapshot naturally has no To-do records. Do not downgrade source as a recovery step.

## Behaviour and implementation

- Duplicate dates came from `DateTimeInput` showing a formatted hint below the native picker. The shared component now renders one native input with `lang="en-AU"`; calendar navigation, semester-break editing and other forms no longer repeat the value underneath. Native picker appearance follows browser/OS language settings. Storage and submitted values remain ISO, and dates displayed elsewhere retain `DD/MM/YYYY` and `h:mm AM/PM` formatting. Do not type ambiguous display strings into database or backup files.
- The timetable's full `DD/MM/YYYY` text was squeezed into a 27px badge intended for month-view day numbers. Week/day headers now use auto-width date labels, separate weekday/date spacing and a rounded today marker. Laptop/tablet columns have a minimum readable width with scrolling inside the calendar when necessary; phone week view remains a vertical list. Events, navigation and break suppression retain their existing logic.
- Semester Progress now uses one bold summary: `QUT Y1S2 | Week 8 of 13`. It wraps safely on narrow cards. Before-start, Semester Break/resume and Teaching complete states remain. The existing progress bar/percentage stays below.
- The floating timer adds a separate, small **Cancel timer** action. Confirmation says that elapsed time will not be saved. Cancel reuses the existing `timer.cancel` transaction, clears the active timer and notifies visible clients through the existing sync channel. It creates no StudySession and does not add time to tasks. The cancelled timer row remains as existing internal timer history. **End** still calls `timer.finish` and opens Study review, where time can be saved or discarded.
- **Tasks → To-do list** appears as its own section before recurring and academic tasks. It is a personal checklist shared across semester filters. Quick add supports Enter, editing is inline, due date is optional, checkboxes complete/uncomplete items, arrows reorder and deletion requires confirmation. Completed items stay available to untick. No subject/semester relationship or conversion flow was added to keep this release small. Optional due dates are display information; they do not create notifications or academic Tasks.
- **Dashboard → Edit Dashboard → Add Widget → To-do list → Done** enables the widget for the current device layout. It shows up to five pending items in manual order, allows quick add and completion, and has View all to open the Tasks checklist. Other pending items fill the preview as items are completed. Existing layouts keep their order/size/visibility; the new widget is initially hidden. Both density settings and themes are supported.
- To-dos are separate `TodoItem` rows in the existing local SQLite database. Writes use the authenticated same-origin productivity API, owner checks, transactions and revision checks. Quick-add request IDs make a retry idempotent and work with plain HTTP LAN access. There is no new npm dependency or server process.
- JSON backups now include `productivity.todoItem`, preserving names, dates, completion and order. Pre-V2.1.3 V2 backups that lack this table still restore, producing an empty To-do list; V1 import remains supported. JSON restore replaces the snapshot and preserves authentication. Do not restore a newer To-do backup using older application code, which does not understand these rows. Full stopped `data`/`.env` copies preserve the entire installation state.
- Existing authentication, origin protection, reminders, Web Push, timer sync, Windows launcher, At startup task and Tailscale Serve architecture are unchanged. `data/`, `.env`, `backups/` and logs remain Git-ignored. Never use seed/reset commands during an update.
