# V2.3 implementation stages

Baseline: V2.2.1, eff83413d49364d201fb059658d66e9784b500ad. Each stage is implemented and checked before the next, with a separate commit. This document is the audit and design checkpoint; the release guide records final validation.

1. Tasks workspace sizing and architecture audit. Shared responsive minimum heights, grid stretch and normal page scrolling preserve V2.2.1's 62/38 layout and content-driven breakpoint. Empty Academic Tasks has an Add task action. DOM/CSS verification is available; no physical responsive success is claimed.
2. Additive scheduling tables, compatible portable backups and shared configured-timezone interval arithmetic. Existing tables and records remain intact.
3. Weekly availability, date overrides, optional preferences and occupied/free interval calculation.
4. Central deterministic engine: existing work, honest estimates, effective deadlines, capacity, sessions and unsaved proposals.
5. Review/edit/selective approval, transactional revalidation, retry safety and guarded undo.
6. Today/Calendar/Timetable and existing timer integration, without duplicating tasks or study accounting.
7. Recorded disruptions produce reviewable alternatives, never automatic changes.
8. Full regressions, migration/backup tests, build/CSS/lifecycle checks, CI and backup-first Acer release/recovery instructions.

## Authoritative planned versus actual relationship

Existing StudySession rows mix manual plans (plannedHours, completed=false) and actual/reviewed study (actualHours). They feed analytics, reminders, timer review and existing JSON backups. Reclassifying or rewriting them would risk real history. They remain intact and visible; uncompleted legacy plans reserve time once in scheduling.

New PlannedWorkBlock rows represent confirmed intentions only. They reference existing Tasks/Assignments/Exams, and optionally an actual StudySession when reviewed work is recorded. Approving a plan does not create a StudySession, update Task completion, assignment progress or actual hours. Calendar integration emits one event per planned block and avoids duplicating a linked actual session. Timer integration reuses the existing timer and its idempotent review/save flow; linking planning context adds no second time ledger.

Availability belongs to the single owner and is optional. dailyHours remains a target, not invented availability. New fixed appointments occupy time; existing classes (including break suppression), exams and legacy plans are reused. Deadlines/informational events do not occupy time. Configured IANA timezone converts civil input into exact instants; interval arithmetic uses half-open [start,end) ranges, merging overlaps before subtraction.

Existing Task actualHours and timer study records must not be summed twice. An explicit remaining estimate is authoritative. An unstarted work item can use its estimate; logged effort on unfinished work needs user review rather than pretending the remainder is exact. Linked tasks replace parent workload for scheduling; estimate gaps are explained, never duplicated. Existing weighted progress is unchanged.

Proposals are temporary previews. A source fingerprint, current-state validation and a single SQLite transaction protect approval from changed availability, work, commitments or reservations. Idempotent approval batches and revision-checked undo protect retries and subsequent edits. No deadline, fixed event, task status or study history is modified by the engine.

## Record not found investigation

The text is emitted by generic deleteRow when its ID no longer exists. Generic save emits a different deleted-on-another-device message, and revision conflicts remain separate. Task conversion and To-do actions use their own authoritative mutations. The workspace refreshes after acknowledged writes and polls/focus-refreshes across devices; an old client can still request deletion of an already-deleted record before refreshing. A disposable-database regression reproduces that legitimate 404 and confirms it cannot delete another record. Completion/reopen retains the original ID; conversion removes only the source To-do atomically (existing regressions retained).

There is no supplied sequence reproducing an erroneous missing-record toast from a valid current row. The screenshot alone cannot establish its cause. No errors are suppressed and no broad backend rewrite is made. If it recurs, record the action, selected row, other-device changes and request status (without private payloads) for diagnosis.
