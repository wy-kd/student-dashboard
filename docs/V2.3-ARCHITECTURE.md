# V2.3 implementation stages

Baseline: V2.2.1, eff83413d49364d201fb059658d66e9784b500ad. Each stage is implemented and checked before the next, with a separate commit. This document is the audit and design checkpoint; the release guide records final validation.

1. Tasks workspace sizing and architecture audit. Shared responsive minimum heights, grid stretch and normal page scrolling preserve V2.2.1's 62/38 layout and content-driven breakpoint. Empty Academic Tasks has an Add task action. DOM/CSS verification is available; no physical responsive success is claimed.
2. Additive scheduling tables, compatible portable backups and shared configured-timezone interval arithmetic. Existing tables and records remain intact.
3. Weekly availability, date overrides, optional preferences and occupied/free interval calculation.
4. Central deterministic engine: existing work, honest estimates, effective deadlines, capacity, sessions and unsaved proposals.
5. Review/edit/selective approval, transactional revalidation, retry safety and guarded undo.
6. Today/Calendar/Timetable and existing timer integration, without duplicating tasks or study accounting.
7. Recorded disruptions produce reviewable alternatives, never automatic changes.
8. Full regressions, migration/backup tests, build/CSS/lifecycle checks, CI and backup-first Acer release/recovery instructions.

## Authoritative planned versus actual relationship

Existing StudySession rows mix manual plans (plannedHours, completed=false) and actual/reviewed study (actualHours). They feed analytics, reminders, timer review and existing JSON backups. Reclassifying or rewriting them would risk real history. They remain intact and visible; uncompleted legacy plans reserve time once in scheduling.

New PlannedWorkBlock rows represent confirmed intentions only. They reference existing Tasks/Assignments/Exams, and optionally an actual StudySession when reviewed work is recorded. Approving a plan does not create a StudySession, update Task completion, assignment progress or actual hours. Calendar integration emits one event per planned block and avoids duplicating a linked actual session. Timer integration reuses the existing timer and its idempotent review/save flow; linking planning context adds no second time ledger.

Availability belongs to the single owner and is optional. dailyHours remains a target, not invented availability. New fixed appointments occupy time; existing classes (including break suppression), exams and legacy plans are reused. Deadlines/informational events do not occupy time. Configured IANA timezone converts civil input into exact instants; interval arithmetic uses half-open [start,end) ranges, merging overlaps before subtraction.

Existing Task actualHours and timer study records must not be summed twice. An explicit remaining estimate is authoritative. An unstarted work item can use its estimate; logged effort on unfinished work needs user review rather than pretending the remainder is exact. Linked tasks replace parent workload for scheduling; estimate gaps are explained, never duplicated. Existing weighted progress is unchanged.

Proposals are temporary previews. A source fingerprint, current-state validation and a single SQLite transaction protect approval from changed availability, work, commitments or reservations. Idempotent approval batches and revision-checked undo protect retries and subsequent edits. No deadline, fixed event, task status or study history is modified by the engine.

## Record not found investigation

The text is emitted by generic deleteRow when its ID no longer exists. Generic save emits a different deleted-on-another-device message, and revision conflicts remain separate. Task conversion and To-do actions use their own authoritative mutations. The workspace refreshes after acknowledged writes and polls/focus-refreshes across devices; an old client can still request deletion of an already-deleted record before refreshing. A disposable-database regression reproduces that legitimate 404 and confirms it cannot delete another record. Completion/reopen retains the original ID; conversion removes only the source To-do atomically (existing regressions retained).

There is no supplied sequence reproducing an erroneous missing-record toast from a valid current row. The screenshot alone cannot establish its cause. No errors are suppressed and no broad backend rewrite is made. If it recurs, record the action, selected row, other-device changes and request status (without private payloads) for diagnosis.

## Stage 2 foundation checkpoint

Migration `20261011060000_v23_planning` creates seven tables: SchedulingPreference, AvailabilityWindow, AvailabilityException, Commitment, WorkEstimate, ScheduleBatch and PlannedWorkBlock, plus indexes/foreign keys. It does not alter or populate any existing table. Optional Task/Assignment/Exam/session/timer links use SET NULL so deleting a plan never deletes work or history, and deleting a source retains the planning intention's title and work key for review. A source deletion removes only that source's new remaining-estimate override in the same existing deletion transaction.

Portable export is format version 3, with a separate scheduling section. V1/V2 import remains supported; importing older snapshots clears newer scheduling records atomically rather than retaining dangling plans. Restores preserve authentication and bump editable revisions. Restored batch history is retained but old undo baselines are invalidated. Scheduling data validates before replacement, references validate inside the transaction, and a failed restore rolls back. Device secrets remain governed by the existing backup rules.

## Stage 3 availability checkpoint

Settings now contains an optional weekly editor with multiple periods, day copying, unavailable-day controls, date-specific replacement/unavailable exceptions, removal/reset and secondary session preferences. Existing dailyHours is labelled as a target. New appointments can be fixed or flexible; both reserve time until explicitly edited. Availability uses one profile revision for the entire atomic edit, so stale changes cannot overwrite another device. Drafts survive rejected saves.

The shared interval adapter recognises recurring classes through the existing calendar/break calculation, exams, legacy uncompleted study plans, appointments and confirmed blocks. Deadlines and informational dates do not reserve time. Linked actual history is not counted a second time. Adjacent planned sessions retain configurable rest spacing. Overnight commitments, overlapping occupied periods and missing availability are supported without inventing free time.

## Stage 4 engine checkpoint

`planning-engine.ts` is the single deterministic scheduling calculation. It reuses existing Tasks, unlinked assignments/exams, parent deadlines and recorded timer/session context; completed work is excluded. Linked Tasks replace parent workload, with estimate gaps explained. Zero/absent durations and logged/partly-completed work require a user-entered remaining estimate instead of guessed effort or percent-complete inference. Approved future minutes reduce unscheduled work, never actual effort or task completion.

The engine ranks effective deadlines first, then explicit priority and larger effort; distributes work across the daily target before filling further available capacity; splits sessions using preferred/minimum duration, rest and explicit daily limits; and reports deadline-specific shortfalls, unknown information and overlapping commitments. Daily target is a soft distribution preference, not invented capacity. Today starts at least five minutes after generation, rounded to the next minute, to leave review time. Supported custom periods are today/future through 14 days; seven days is the default. Generated proposals do not write planning/history records. Existing schema has no explicit Task prerequisite graph; the engine does not invent one from template names or ID order.

Stage 4 passed 18 focused tests and typecheck: deterministic previews, seven-day distribution, exact parent due times, priorities, multi-session tasks, missing data, planned/actual separation, no duplicate parent workload, deadline distribution, session/rest/daily limits, exclusions, explicit estimate revisions and source cleanup, plus foundation/availability regressions.

## Stage 5 review and approval checkpoint

Study contains Plan my week / tomorrow / remainder of today, a bounded custom period, exclusions and remaining-estimate controls. The inline preview separates existing commitments/confirmed work, unconfirmed blocks, conflicts, unknown durations and shortfalls. Users can edit times, titles/durations and work associations, remove/deselect suggestions, reserve extra time, regenerate or cancel. Manual outside-availability overrides are explicit and retain deadlines/occupied-time/maximum-workload checks. A saved entirely unavailable week is known zero capacity, rather than missing setup. Preview/approval is bounded to 200 blocks per request.

Approval checks a SHA-256 fingerprint of current planning sources inside the SQLite transaction, then revalidates every selected interval, source, deadline, daily maximum, rest gap and moved-record revision. Locked sessions require explicit unlocking. Approval UUIDs plus payload hashes make retries idempotent and reject reuse for different changes. An interrupted response retains exactly the original approval request and freezes editing until retried; after a full page reload, inspect confirmed sessions before regenerating. Session overlap validation still prevents duplicate reservations if client state is lost. No approval writes Task completion or StudySession records.

Batches retain created/moved baselines. Undo deletes only untouched created intentions and restores unchanged moved intentions after rechecking original slots against current constraints. It rejects active timers, recorded work, newer revisions and new conflicts. It preserves unrelated plans, Tasks and history. Restored backup batches cannot apply old undo baselines.

Stage 5 passed 28 focused tests and typecheck, including actual React preview editing/selective approval/cancel/uncertain-response retries; atomic/idempotent persistence; stale work/availability; exact deadlines; fixed/selected/rest/max conflicts; guarded moves/undo; recorded-history protection; and competing concurrent approvals. Foundation, availability and engine regressions remain green.

## Stage 6 integration checkpoint

Today separates intended, recorded, future confirmed allocation and remaining known availability from the daily target. Scheduled and due/overdue Tasks are shown once. Confirmed plans and appointments use the existing Calendar/Timetable; linked actual StudySessions are retained in history but are not duplicated as Calendar events. Study and assessment detail pages link plans back to the original work. Semester selection scopes academic work while all physical commitments still reserve capacity.

Starting a confirmed plan uses the existing synchronised timer with authoritative work links and intended duration (one countdown, capped at the existing 240-minute limit). Pause/Resume/End and review remain unchanged. Saving links one actual StudySession to its plan; planned and actual hours stay distinct, and remaining effort requires explicit review rather than subtracting elapsed time. Discard records nothing. A separate explicit manual review can record earlier work idempotently without a timer or Task completion. Plan edits use the same guarded approval path; active timers and recorded history protect removal/undo.

Shared civil-date helpers were extracted without changing their behavior to avoid a Calendar/time utility import cycle. Stage 6 passed 48 focused integration, React DOM, engine, approval and existing timer/productivity tests, typecheck, production build and emitted CSS verification. No physical device tests are claimed.
