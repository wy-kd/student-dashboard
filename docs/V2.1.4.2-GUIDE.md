# V2.1.4.2 — Fixed timer, Hours/Minutes and Dashboard layout

UI/UX correction only. No migration, dependency, existing-record, authentication, timer persistence/sync, backup-format or infrastructure change. No Spotify.

## Behaviour

- The floating card is fixed lower-right on desktop/iPad, capped at 360px wide, with 20px/safe-area margins. Width is constrained to the space beside the expanded/collapsed sidebar. Phone placement is above the 62px bottom navigation with a 14px gap and safe-area allowance. No background dock spans the screen.
- All drag/grip/corner/snapping/storage code and obsolete tests/styles are removed. An old corner value left in an existing browser is never read or written. Other localStorage preferences remain intact. A small visual-viewport listener only supplies keyboard clearance and visible height to CSS; there are no movement gestures or orientation-selected positions. Very short viewports allow internal card scrolling. On phones at most 600px wide, the modal navigation drawer temporarily hides the card while open, so it cannot cover navigation; the timer continues and closing the drawer restores the fixed card.
- Running/Paused show the floating card. End synchronises review and opens Study; the floating surface is absent in review, saved and discarded states. No Cancel, Ready to save or Review & save UI returns. The Study review retains notes, linked tasks, Save/Discard and duplicate-session protection.
- Review has labelled Hours and Minutes numeric inputs (`inputMode="numeric"`, integer step). Hours must be an integer 0–24, minutes an integer 0–59 and the combined total at most 1,440. Empty, negative, decimal/non-numeric and out-of-range inputs are rejected, with native field validation plus an explicit combined-duration message. Submitted minutes are `hours × 60 + minutes`; the server still stores its existing actual-hours format.
- Initial review values use the server-authoritative `focusMs` after End. No countdown target or competing elapsed-time calculation is used; pauses/breaks stay excluded. Round to the nearest whole minute with `Math.round(focusMs / 60000)`: under 30 seconds → 0, exactly 30 seconds → 1, 59 seconds → 1, 60 seconds → 1. This replaces decimal presentation only and does not modify persisted timer milliseconds or previous sessions. Zero remains permitted by the existing save validation; it records zero actual hours. A long session beyond the existing 24-hour save limit must be edited before saving.
- Dashboard metadata: `DD/MM/YYYY · Week N of M`, small/muted above Dashboard. Semester Progress: semester name on one line and `Week N of M` on the next; no summary date, with progress percentage/bar unchanged. Both use the existing shared teaching-week calculation. Break/resumption, before-start and teaching-complete wording remain correct. Shared Analytics semester display follows the same clean hierarchy.

## Before updating

Use **Command Prompt**, not PowerShell, and run commands individually. These instructions assume `C:\Projects\student-dashboard` and task `Student Dashboard`. Finish/save an active study session if practical and close other clients during maintenance. Export fresh JSON while the app is running. Keep backups private and outside Git. Use the existing Node 24 installation required by the repository. No data restore is part of a normal update.

## A. Backup before update

1. While the application is still running, open **Settings → Semesters & data maintenance → Backups & data export → Export JSON backup**. Save this fresh export in your Downloads folder as `student-dashboard-before-v2.1.4.2.json`. If that name already exists, retain the old export elsewhere and ensure this path refers to the new export, not an earlier download.
2. Disable automatic startup and gracefully stop the dashboard:

```bat
cd /d "C:\Projects\student-dashboard"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
```

Continue only when the launcher reports Stopped and port 3000 is free. Disabling the task alone does not stop the application. Close other browser clients for maintenance.

3. Create a dated full backup outside the repository. Keep this Command Prompt open: later commands use its `SD_BACKUP` variable. The timestamp prevents overwriting an earlier backup. `%I` below is for an interactive Command Prompt, not a batch file.

```bat
for /f %I in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd-HHmmss"') do set "SD_BACKUP=C:\StudentDashboardBackups\%I-before-v2.1.4.2"
mkdir "%SD_BACKUP%"
copy /B "%USERPROFILE%\Downloads\student-dashboard-before-v2.1.4.2.json" "%SD_BACKUP%\portable.json"
robocopy "data" "%SD_BACKUP%\data" /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ
copy /B ".env" "%SD_BACKUP%\.env"
echo %SD_BACKUP%
npm run db:backup
```

For example, the folder might be `C:\StudentDashboardBackups\2026-09-08-153000-before-v2.1.4.2`. Write down the **actual folder printed**. Robocopy exit codes 0–7 are successful/non-fatal; 8 or higher means failure. Check its summary has zero failed files. `copy` must report one file copied for each file. The `data` copy includes `student.db`, any SQLite sidecars and other local runtime files. The extra `npm run db:backup` JSON is saved in `C:\Projects\student-dashboard\backups`; it does not replace the external backup. Keep these files private because the full copy contains authentication and push credentials.

## D. Recovery if records are missing

First check semester selection and filters. If a restore is needed, stop using the app on other devices and keep the scheduled task disabled. Restoring JSON **replaces academic/productivity records with the backup snapshot**, rather than merging them. Later edits will be replaced. The current data is backed up first and restore runs in a transaction. Existing passwords and sessions are not replaced by JSON.

### Restore through Settings when the app works

1. Keep the task disabled and run the dashboard manually using `node scripts/windows/dashboard.mjs start` from `C:\Projects\student-dashboard` if it is stopped. Do not start a second copy.
2. Sign in at `http://localhost:3000`.
3. Open **Settings → Semesters & data maintenance → Backups & data export → Restore a backup → Choose JSON backup**.
4. Select `portable.json` inside the **actual dated external backup folder** printed in step A, for example `C:\StudentDashboardBackups\2026-09-08-153000-before-v2.1.4.2\portable.json`.
5. Confirm replacement, wait for “Backup restored” and reload every open client. Verify records with All semesters and appropriate filters.
6. Only after verification, stop the manual app and enable/run the scheduled task using the commands in section C. The pre-restore JSON copy is in `C:\Projects\student-dashboard\backups`.

### Restore JSON through CLI

In a new Command Prompt, set `SD_BACKUP` to the actual backup folder you wrote down (replace the example timestamp). Do not continue while the app or port 3000 is active:

```bat

The CLI uses the same validation, transaction and automatic pre-restore backup as Settings. If the database is damaged so that JSON restore cannot read/back up its current contents, use the full-copy recovery below.

## E. Recovery if the database or application is damaged

Use this only with a verified full backup. It restores the entire database, credentials and local runtime state at the backup time. Keep the old damaged files for investigation; do not merge an old `student.db` with newer SQLite WAL/SHM files.

1. Stop the dashboard and verify port 3000 is free:

```bat
cd /d "C:\Projects\student-dashboard"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
```

If the launcher cannot confirm a safe stop/free port, do not copy a database over a running process. Resolve that failure first.

2. Select the actual full backup folder, check it exists and create a separate dated holding folder for the current state:

```bat
set "SD_BACKUP=C:\StudentDashboardBackups\2026-09-08-153000-before-v2.1.4.2"
dir /a "%SD_BACKUP%\data\student.db"
dir /a "%SD_BACKUP%\.env"
for /f %I in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd-HHmmss"') do set "SD_HOLD=C:\StudentDashboardBackups\%I-before-recovery"
mkdir "%SD_HOLD%"
if exist "data" move "data" "%SD_HOLD%\data"
if exist ".env" move ".env" "%SD_HOLD%\.env"
```

Continue only if the old `data` directory and `.env` were moved successfully (or did not exist). The target `C:\Projects\student-dashboard\data` must not exist before the copy below. This avoids mixing database generations.

3. Restore the complete directory and environment file:

```bat
robocopy "%SD_BACKUP%\data" "data" /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ
copy /B "%SD_BACKUP%\.env" ".env"
dir /a "data\student.db"
dir /a ".env"
```

Check zero failed files in the Robocopy summary and one environment file copied. Re-run the hash verification command from section B: it now compares the restored files against the backup. Do not touch `backups`, and do not run seed/reset/destructive Prisma commands.

4. Repair installed dependencies/build if needed, then validate and start:

```bat
npm install
npm test
npm run typecheck
npm run build
node --import tsx --test tests/startup-production.integration.ts
node scripts/windows/dashboard.mjs start
```

Sign in with the password valid at the full-backup time and verify your records. Use a second terminal for status/logs. Only then stop the manual app and enable/run the scheduled task as in section C. Keep `SD_HOLD` and the original backup until recovery is confirmed. Keep the V2.1.4.2 source. The V2.1.4.1 backup has the same schema; this patch adds no migration. Existing checked-in migrations still run safely if restoring a much older snapshot. Do not downgrade source as a recovery step.

## Device acceptance checks

Reload browsers/PWAs. Verify existing records, study history and totals before testing new sessions. Check localhost, LAN and the existing private Tailscale URL.

- Desktop: lower-right fixed card in expanded/collapsed sidebar, narrow/short browser sizes, light/dark themes and Comfortable/Compact density. No grip or movement should exist.
- iPad: portrait/landscape, expanded/collapsed navigation, browser and installed PWA. Entire card/buttons must stay beside navigation and within the screen. Test resizing/rotation; no corner memory should affect placement.
- Phone: portrait/landscape, safe-area/home-indicator and bottom navigation clearance, no horizontal overflow. Open the review keyboard; numeric Hours/Minutes must remain readable, and Save/Discard reachable by scrolling. An active card must remain above the keyboard; internally scroll it in very short viewports. Open/close the narrow modal navigation drawer and confirm timer continuity.
- Start a 50-minute countdown and End early: only elapsed active study time is proposed. Also test stopwatch and a paused period. Review 30/60/75/130 minutes as 0:30/1:00/1:15/2:10. Try blank/decimal/negative minutes and 60 minutes; all must be rejected. Try 24 hours + 1 minute; combined limit must reject it. Under 30 seconds proposes zero, not a silently inflated minute.
- Pause on one device, Resume from another, End from the floating card: initiating device opens Study review, both clients hide floating timer after sync, and no StudySession is automatically created. Save once and verify one session with correct actual hours/notes. End another and Discard; no session is added.
- Dashboard: `11/10/2026 · Week 11 of 13` for that date/semester fixture; real installation uses its current date/week. Progress card shows semester name and Week N of M separately, not the date. Check break/resumption and before/complete states where applicable.
- After Task Scheduler is re-enabled, perform your real reboot test and private remote access test. Tailscale Run unattended, Serve --bg and application startup configuration are unchanged.
