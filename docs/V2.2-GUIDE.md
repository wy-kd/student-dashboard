# V2.2 — Assignment Breakdown & Task Integration

No database migration or dependency is added. Existing assignments, Task relationships, StudySessions, passwords, sessions and backup format are preserved. Windows startup, Task Scheduler, Tailscale, timer synchronisation, recurring tasks, reminders, Web Push and PWA infrastructure are unchanged. No Spotify or external AI API is included.

## Using V2.2

- **Create an assignment:** required name, subject and due date/time are grouped together; optional workload/weighting and additional fields remain available. Australian date/time display is retained. After the server saves the assignment, choose **Break into tasks** or **Maybe later**. Skipping/cancelling never deletes the saved assignment. Existing assignments also have **Break into tasks** in Assignment Details.
- **Manual breakdown:** add, rename, edit, move up/down or remove unsaved task rows. Optional fields include description/notes, due date/time, estimated hours, priority and status. Save only selected rows, up to 50 per batch. Blank estimates mean zero; no StudySession/actual hours are invented.
- **Suggestions:** Research report, Programming assignment, Presentation and General assignment templates work offline without any API. Loading suggestions changes only the draft. Deselect or remove unwanted suggestions, change details or add manual steps before explicitly saving.
- **Safe saves:** each breakdown batch is atomic and uses stable Task IDs for retries. If a response is lost, retry the same locked draft. Successful retries acknowledge existing Tasks without overwriting later edits or completion. If part of a previously saved batch was deleted, review the assignment rather than recreate it through that pending batch. Never create a fresh batch to retry an uncertain save. The pending draft is kept in sessionStorage for this browser tab/origin and can be reopened after refresh; no refresh automatically saves anything. Different devices/hostnames do not share unsaved drafts. If browser storage is blocked or the tab is closed, inspect Assignment Details for an uncertain save before drafting again. Assignment/individual Task creation also uses a stable request ID for an in-dialog retry.
- **Assignment tasks:** complete/reopen, edit, add another Task or start Focus from the same records used by Tasks and Today. Task rows include due date/time, estimate and a parent assignment link. Details shows completion count, task estimates completed/remaining, next outstanding task and the existing assignment progress bar. Reorder controls apply to unsaved drafts, not a new persistent task-order system.
- **Progress:** the existing estimate-weighted calculation is unchanged. Zero-estimate Tasks count as weight one; assignments without Tasks use manual progress; Submitted remains 100%. Before a first linked Task, the form warns that task-based progress will replace the displayed manual percentage. The stored manual value is retained. Workload forecasts continue using the existing remaining-work calculation without adding assignment and linked-task estimates twice. Task estimate summaries are estimates, not actual study time.
- **Today:** existing due-today/overdue Tasks share the completion control. Upcoming assignment Tasks cover the next seven days. Undated next steps follow existing assignment priorities. View all Tasks for the complete list; its default filter is Today. No automatic Plan My Day/Week generator returns. Focus uses the existing timer and its existing active-timer protection; starting Focus does not complete the Task.
- **To-dos:** remain a lightweight checklist. **Convert to Task** explicitly opens a prefilled form with optional subject/assignment, due date/time and estimate. Assignment selection inherits its subject. Title and completion state are prefilled; a date-only To-do defaults to 17:00 on that date and is editable. Only after the Task is created does the same transaction remove the To-do. Invalid/stale submissions preserve the original. Retrying an uncertain successful conversion acknowledges the same destination Task. The original To-do has no completion timestamp/history field; a completed conversion uses the existing Task completion timestamp behaviour at conversion time. Existing StudySessions are untouched.
- **Semester Progress:** one strong text element displays **QUT Y1S2 | Week 11 of 13** with identical font, size, weight, colour and line height for both parts. It wraps naturally without truncation. Break/before-start/teaching-complete and week-resumes information still use the shared calculation. Dashboard retains its separate small `DD/MM/YYYY · Week N of M` header; the progress percentage/bar is unchanged.

## Before updating

Use **Command Prompt**, not PowerShell, and run commands individually. These instructions assume `C:\Projects\student-dashboard` and task `Student Dashboard`. Finish/save an active study session if practical and close other clients during maintenance. Export fresh JSON while the app is running. Keep backups private and outside Git. Use the existing Node 24 installation required by the repository. No data restore is part of a normal update.

## A. Backup before update

1. While the application is still running, open **Settings → Semesters & data maintenance → Backups & data export → Export JSON backup**. Save this fresh export in your Downloads folder as `student-dashboard-before-v2.2.json`. If that name already exists, retain the old export elsewhere and ensure this path refers to the new export, not an earlier download.
2. Disable automatic startup and gracefully stop the dashboard:

```bat
cd /d "C:\Projects\student-dashboard"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
```

Continue only when the launcher reports Stopped and port 3000 is free. Disabling the task alone does not stop the application. Close other browser clients for maintenance.

3. Create a dated full backup outside the repository. Keep this Command Prompt open: later commands use its `SD_BACKUP` variable. The timestamp prevents overwriting an earlier backup. `%I` below is for an interactive Command Prompt, not a batch file.

```bat
for /f %I in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd-HHmmss"') do set "SD_BACKUP=C:\StudentDashboardBackups\%I-before-v2.2"
mkdir "%SD_BACKUP%"
copy /B "%USERPROFILE%\Downloads\student-dashboard-before-v2.2.json" "%SD_BACKUP%\portable.json"
robocopy "data" "%SD_BACKUP%\data" /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ
copy /B ".env" "%SD_BACKUP%\.env"
echo %SD_BACKUP%
npm run db:backup
```

For example, the folder might be `C:\StudentDashboardBackups\2026-10-10-153000-before-v2.2`. Write down the **actual folder printed**. Robocopy exit codes 0–7 are successful/non-fatal; 8 or higher means failure. Check its summary has zero failed files. `copy` must report one file copied for each file. The `data` copy includes `student.db`, any SQLite sidecars and other local runtime files. The extra `npm run db:backup` JSON is saved in `C:\Projects\student-dashboard\backups`; it does not replace the external backup. Keep these files private because the full copy contains authentication and push credentials.

Confirm the counts match the records you expect, the files have non-zero sizes and the extra local JSON has today's timestamp. Verify every copied data file and `.env` against the stopped originals without printing their contents:

```bat
powershell -NoProfile -Command "$ErrorActionPreference='Stop'; $src=Join-Path (Get-Location) 'data'; Get-ChildItem -LiteralPath $src -File -Recurse | ForEach-Object { $dest=Join-Path ($env:SD_BACKUP+'\data') $_.FullName.Substring($src.Length+1); if ((Get-FileHash -LiteralPath $_.FullName).Hash -ne (Get-FileHash -LiteralPath $dest).Hash) { throw 'Data copy mismatch' } }; if ((Get-FileHash -LiteralPath '.env').Hash -ne (Get-FileHash -LiteralPath ($env:SD_BACKUP+'\.env')).Hash) { throw 'Environment copy mismatch' }; Write-Output 'Full backup verified'"
```

Do not pull if verification fails. A parse/count check is not a restore rehearsal; retain both JSON and the complete stopped database copy.

## D. Recovery if records are missing

First check semester selection and filters. If a restore is needed, stop using the app on other devices and keep the scheduled task disabled. Restoring JSON **replaces academic/productivity records with the backup snapshot**, rather than merging them. Later edits will be replaced. The current data is backed up first and restore runs in a transaction. Existing passwords and sessions are not replaced by JSON.

### Restore through Settings when the app works

1. Keep the task disabled and run the dashboard manually using `node scripts/windows/dashboard.mjs start` from `C:\Projects\student-dashboard` if it is stopped. Do not start a second copy.
2. Sign in at `http://localhost:3000`.
3. Open **Settings → Semesters & data maintenance → Backups & data export → Restore a backup → Choose JSON backup**.
4. Select `portable.json` inside the **actual dated external backup folder** printed in step A, for example `C:\StudentDashboardBackups\2026-10-10-153000-before-v2.2\portable.json`.
5. Confirm replacement, wait for “Backup restored” and reload every open client. Verify records with All semesters and appropriate filters.
6. Only after verification, stop the manual app and enable/run the scheduled task using the commands in section C. The pre-restore JSON copy is in `C:\Projects\student-dashboard\backups`.

### Restore JSON through CLI

In a new Command Prompt, set `SD_BACKUP` to the actual backup folder you wrote down (replace the example timestamp). Do not continue while the app or port 3000 is active:

```bat
cd /d "C:\Projects\student-dashboard"
set "SD_BACKUP=C:\StudentDashboardBackups\2026-10-10-153000-before-v2.2"
schtasks /Change /TN "Student Dashboard" /Disable

```

Wait for “Backup restored. Previous data saved in backups/.” before starting. Verify records in the browser, then stop and enable/run the task as in section C. The CLI uses the same validation, transaction and automatic pre-restore backup as Settings. If the database is damaged so that JSON restore cannot read/back up its current contents, use the full-copy recovery below.

## E. Recovery if the database or application is damaged

Use this only with a verified full backup. It restores the entire database, credentials and local runtime state at the backup time. Keep the old damaged files for investigation; do not merge an old `student.db` with newer SQLite WAL/SHM files.

1. Stop the dashboard and verify port 3000 is free:

```bat
cd /d "C:\Projects\student-dashboard"
schtasks /Change /TN "Student Dashboard" /Disable
node scripts/windows/dashboard.mjs stop
node scripts/windows/dashboard.mjs status
```

If the launcher cannot confirm a safe stop/free port, do not copy a database over a running process. Resolve that failure first.

2. Select the actual full backup folder, check it exists and create a separate dated holding folder for the current state:

```bat
set "SD_BACKUP=C:\StudentDashboardBackups\2026-10-10-153000-before-v2.2"
dir /a "%SD_BACKUP%\data\student.db"
dir /a "%SD_BACKUP%\.env"
for /f %I in ('powershell -NoProfile -Command "Get-Date -Format yyyy-MM-dd-HHmmss"') do set "SD_HOLD=C:\StudentDashboardBackups\%I-before-recovery"
mkdir "%SD_HOLD%"
if exist "data" move "data" "%SD_HOLD%\data"
if exist ".env" move ".env" "%SD_HOLD%\.env"
```

Continue only if the old `data` directory and `.env` were moved successfully (or did not exist). The target `C:\Projects\student-dashboard\data` must not exist before the copy below. This avoids mixing database generations.

3. Restore the complete directory and environment file:

```bat
robocopy "%SD_BACKUP%\data" "data" /E /COPY:DAT /DCOPY:DAT /R:1 /W:1 /XJ
copy /B "%SD_BACKUP%\.env" ".env"
dir /a "data\student.db"
dir /a ".env"
```

Check zero failed files in the Robocopy summary and one environment file copied. Re-run the hash verification command from section B: it now compares the restored files against the backup. Do not touch `backups`, and do not run seed/reset/destructive Prisma commands.

4. Repair installed dependencies/build if needed, then validate and start:

```bat
npm install
npm test
npm run typecheck
npm run build
node --import tsx --test tests/startup-production.integration.ts
node scripts/windows/dashboard.mjs start
```

Sign in with the password valid at the full-backup time and verify your records. Use a second terminal for status/logs. Only then stop the manual app and enable/run the scheduled task as in section C. Keep `SD_HOLD` and the original backup until recovery is confirmed. Keep the V2.2 source. The V2.1.4.2 backup has the same schema; V2.2 adds no migration. Existing checked-in migrations still run safely if restoring a much older snapshot. Do not downgrade source as a recovery step.

## Validation scope

The regression suite uses disposable SQLite databases and covers assignment validation/idempotent creation, optional drafts/templates/selection/reordering, atomic linked Task creation and retry/rollback, weighted/manual/zero-estimate/submitted progress, forecast accounting, rendered Today/Details/Tasks, atomic To-do conversion and stale/error handling, authentication/same-origin checks, backup/restore/CSV and retained credentials/history. Existing timer, recurring-task, reminder, Web Push and other regressions remain. Build runs emitted production CSS verification; the separate integration suite checks real production startup/readiness/graceful stopping with disposable data.

Live responsive browser/touch testing was unavailable in this execution environment (no local browser binary; the cloud browser cannot reach this workspace server). Render/CSS tests do not establish physical Acer, iPad, phone, installed-PWA, keyboard, Task Scheduler or reboot behaviour. Perform the checklist above locally; no physical-device success is claimed.
